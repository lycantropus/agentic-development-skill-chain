# Handoff Refinement

Refine a product-owned handoff into evidence-backed engineering inputs without taking ownership of its product requirements. This optional receiving workflow precedes architecture; the existing linear chain needs no additional files or approvals.

## Inputs and ownership

Read [the input contract](references/input-contract.md) for the authoritative manifest schema, resolver commands and readiness rules, and [the run layout](references/run-layout.md) for where everything is stored and how provenance is declared. Reuse the inventory from [delivery-workspace](../2d_delivery-workspace/SKILL.md), including portable repo keys and machine-local checkout bindings. Missing coordination identity or checkout setup belongs to that skill; do not initialize another coordination repo for each package. An agreed tracked location in one code repo is sufficient for single-repo work.

Product owns the immutable baseline and explicit product responses. Engineering owns evidence, technical constraints and implementation decisions. Architecture and plans derive from those inputs; neither engineering judgment nor model review grants product approval. Contradictions get an owner and block affected scope, with no blanket engineering-over-product precedence.

Write new refinement, exchanges and handoff prompts in English. Preserve source identifiers, verbatim ACs/evidence and intended product localization. Never translate or rewrite a received requirement to satisfy a local validator.

## Receive and inspect

1. Preflight source versus target before creating artifacts or ownership mappings: read the package’s declared deliverable and establish the source package, receiving location and intended deliverable (for example, lab prototype versus production). If any distinction is unresolved, ask one compact question naming all three; a corrected path or the current directory does not decide scope. Reuse explicit answers already given. Identify package version/source, product owner, affected repo keys and agreed coordination location. Pin consumed shared inputs to a commit or content hash. Distinguish local drafts, proposed PR revisions and accepted team revisions; a local commit is not team acceptance.
2. Decide resume or new run per [the run layout](references/run-layout.md): list `runs/`, resume the current run if its handoff version and examined baselines still hold, otherwise create `runs/<YYYY-MM-DD-NN>/` and name the predecessor. Use [package-tools](references/package-tools.md) for byte copies, hashes, selected complete AC ranges and detached return-link checks. Preserve every received file byte-identical under `runs/<run-id>/handoff/<version>/` with integrity metadata. Do not rewrite links inside the received copy, require a numbered source layout, or write into a generated `2b_handoff/` run. Keep prior versions and prior runs. Create only folders with actual content, and write the run README's provenance table before producing any other result.
3. Compare the manifest/README’s prototype inclusion decision and format with the received files. Preserve the decision; do not ask again merely because the package changed hands. Record actual prototype mode: standalone interactive HTML or a pinned runnable bundle/source revision with start instructions when available, static references or none otherwise, plus simulated/missing behavior. A promised prototype that is missing, inaccessible or lacks required start instructions is a package discrepancy: report it through product feedback and assess the affected blocking scope rather than silently accepting static references as fulfillment. For older packages without an inclusion decision, record it as unspecified and assess the available references without inventing a decision. Prototypes inform interaction, not production architecture; intentionally static references alone are not a universal blocker. The reverse also holds: a client-only or simulated prototype does not narrow the baseline. Derive production scope from the ACs, not from what the prototype implements.
4. Establish an **Engineering direction checkpoint** before deep implementation design: state the proposed direction, its explicit engineering authority, and any superseded proposal. Make it cheap for the developer to correct reuse versus replacement or runtime choices; existing code remains behavior evidence, not authority over the intended technology. Keep these decisions in engineering constraints, outside Product feedback, and do not treat them as product approval. Inspect relevant code in the identified repositories. With several repositories or large codebases, delegate one read-only inspection per repository using [the evidence brief](references/evidence-brief.md) and verify a cited location per result before use; the lead keeps the developer discussion and all classification. Cite repo key, commit, path and relevant evidence; distinguish implemented behavior from proposed behavior. Record testable engineering requirements separately, linked to source ACs or explicit engineering authority. Never weaken a product AC by relabeling it technical. Keep implementation details inside the product story unless the work has an independently verifiable technical outcome; then declare an optional engineering story under the input contract, with rationale, authority, criteria and dependencies. Do not manufacture a product PRD for it.
5. Read each repo's intake status from workspace onboarding. Run the read-only `workspace.mjs baseline` applicability report from delivery-workspace against the seal and examined revision; record ancestry, curated-file presence/equality and remote acceptance separately. Commit existence or `local-sealed` alone is insufficient. A divergent but equivalent baseline may be reusable; missing documents or divergent unequal baselines need a `baseline` prerequisite for the affected repository and reconciliation, not an automatic fresh intake or a claim that code is broken. Reuse its applicable accepted baseline revision. An incomplete intake resumes with its owner; suspected drift needs an explicitly chosen audit. Planned repos route to bootstrap with approved scope. Read-only investigation and product questions may proceed before all baselines are ready, but downstream readiness remains per repository.

## Scope before binding mappings

Keep three things apart and record each on its own in `runs/<run-id>/refinement/findings.md`: the complete source inventory (every AC of the received baseline, with `sourceId` and verbatim range), the investigation assignment (which repository was inspected for which ACs), and the binding implementation and verification ownership. Inspecting a repository does not make it the owner. When the source describes a prototype, a separate system or a repository outside the delivery scope, say so and leave ownership open; do not assign those ACs to the inspected repository because the validator wants a mapping.

While scope or ownership is unresolved, write the inventory with `repositories: []` for the open requirements and no mappings for them; `chain check inputs --allow-blocked` then reports `ownership unresolved: <id>` and `selected repository has no resolved scope` as honest blockers. Without the flag the inventory stays non-consumable, so no architecture, plan or execution gate can run on invented scope. An ownership question that spans a whole deliverable references every AC of that deliverable; a narrower question references only the criteria it actually affects. Prototype ACs are assessed as prototype ACs: production questions about hosting, operations or scale block the production scope, not an explicitly separate prototype evaluation. Keep authorized engineering constraints for planned services in `engineering` with `story: null` until a real local story can be bound; record missing checkout/state/baseline prerequisites in the same input marker. Do not invent a local PROJ or initialize every investigated repository. Record every assumption about the source as an assumption with its evidence, never as a fact.

## Local project state

For each selected implementation repository with a bound checkout, establish its local PROJ ID and create `specs/PROJ-<X>-<theme>/` while placing its actual refinement inputs. Resolve `<installed-5_executing>` to `~/.codex/skills/5_executing` for Codex or `~/.claude/skills/5_executing` for Claude. From that checkout root, run `bash <installed-5_executing>/scripts/chain state init <X> <theme>` before its refinement review and architecture handoff. This replaces Concept's initialization on the external-entry route: a new state is `CP1:pending`, and an existing state is retained unchanged by the idempotent helper. Never reset a resumed project or infer CP1 approval from received product approval; only the Step 5 checkpoint may approve CP1.

Keep execution state in its owning implementation repository, not the shared coordination project or portable input bundles. If a checkout is unavailable, record initialization as a receiving-refinement prerequisite in its onboarding prompt; do not invent a checkout or initialize another repository's state in coordination. Record review defects with the existing findings helper; it creates the stage ledger when needed, including before state exists. Do not hand that repository to architecture until local initialization and readiness checks are complete.

## Repeat rounds and package consistency

Before a baseline recommendation and again before closing a long review, compare supplied source context/pins with the source revision currently available, using `package-tools.mjs source-status` when a source checkout and packaged commit exist. Record the compared revisions, changed paths and any known unexported behavior changes; missing source access is missing evidence. Live source is context only: request source-side reconciliation/new packaging for relevant changes, retain every frozen AC until explicitly amended, and add a `source-reconciliation` prerequisite for affected repositories. Never silently consume a newer concept.

On repeat rounds, compare current inputs with the previous consumed baseline and responses. Identify changes to requirements, approved product answers, shared rules, relevant engineering constraints and interface contracts; cite the revisions and affected requirement IDs. Record missing comparison evidence rather than claiming no change. Re-evaluate affected requirements even when their source bytes are unchanged: the delta directs attention, not review exemptions.

First assess current requirements against current authoritative inputs without using prior findings as the analysis outline. Then reconcile every earlier finding and product question: still open, resolved with cited evidence, superseded with a replacement reference, or requiring reassessment with a reason. Preserve IDs and applicable baselines in the existing findings or feedback artifacts, using their existing statuses rather than introducing another ledger or machine-readable status vocabulary. No new findings does not mean old questions are answered.

Question, finding and evidence IDs are allocated once per project across all runs. Before assigning a new ID, scan earlier runs and `product-feedback/` rounds for the highest used number and continue from there; never reuse an ID for a different matter, even if the earlier item was a draft. Earlier unapproved drafts, including runs that never reached review, get a disposition in the current run (carried, superseded, withdrawn) but contribute no decisions: their "fixed" or "resolved" marks were made against their input state and do not count as agreement on the current baseline.

Avoid repeating a question only when an accepted decision still applies to the current baseline; cite that decision and the applicability check. Changed requirements, constraints or counterevidence require reassessment. Proposed, superseded or deprecated decisions cannot silently close questions. A technical decision is not product approval, a documented design is not implementation evidence, and implementation evidence is not integration acceptance.

Check package-wide consistency of states, roles, terminology and shared rules, including compatible preconditions and outcomes at cross-PRD transitions. These checks may run as parallel consistency briefs per topic (see the evidence brief); workers return candidates, the lead decides. When a finding exposes a reusable diagnostic, apply it to other relevant requirements; search for assumptions behind the old rule, not only its wording or ID. Keep one issue identity with all affected references. Record a brief reason for material suspected impacts found not applicable, without an exhaustive negative-check report. Route cross-project impacts to their owners without editing sibling scope. These checks supplement AC ownership, coverage and integration verification.

## Product feedback and responses

Classify each issue as product question, engineering decision, code/integration gap or missing evidence, and name the kind of decision it needs: a product decision, a technical investigation, an architecture decision or a later operations/release decision. Only the first goes to Product; the other three stay with engineering and must not be recorded as product blockers. Do not bundle them into one scope blocker: parsing, APIs, queues or storage behind a clear AC are engineering decisions; whether a role, notification or workflow exists at all is a product question. Discuss engineering decisions with the developer in this session and record the outcome with its rationale as an engineering constraint or optional engineering story; they do not go back to product and do not block scope. Only genuine product gaps become product questions, each with the smallest blocking scope it actually affects. Each question must be answerable on its own and state: the evidence, the concrete decision requested, the recommendation with alternatives, the impact of each, the responsible role and the exact work step that waits for it. Give product questions stable IDs, baseline/source AC references to the actually affected criteria (never a whole PRD when only some criteria are concerned), concrete evidence, alternatives and impacts, owner and blocking scope. The machine-readable `blockingRepositories` must match the prose: a question that the prose calls non-blocking for a repository must not list that repository. Keep them in `runs/<run-id>/refinement/product-feedback/<round>/`, separate from engineering review findings. Use [the feedback and handoff format](references/feedback-and-readiness.md) to prepare a portable return package with sufficient excerpts and evidence to answer without this checkout. Do not send or publish it without explicit authorization.

Ingest only explicit product responses with question ID, owner, date and applicable baseline. An informal suggestion stays a proposal; silence, a clean review, an open PR or a developer's assumption cannot close the question. Retain response provenance and original source bytes. For a superseding package, preserve the prior version and reconcile affected questions, requirements, architecture, plans and tests; approvals against an old baseline do not transfer automatically. Reconcile concurrent team edits and upstream answers before updating readiness.

Product-owned source changes run through `review-reconcile` in the source project; `handoff-package` emits a new dated package when needed. The receiver never edits the original PRDs, even in a copied local product-authoring folder.

## Review and readiness

Create `external-handoff.json` and refinement mappings according to the input contract. Validate with the resolver; a present malformed marker must fail, not fall back to linear inputs. Use its blocked-inspection option only to investigate and prepare feedback, never to authorize architecture or execution.

Before requesting the independent review, run this self-check and record its result in the run README:

- Prose and machine-readable blockers agree: every `blockingRepositories` entry and every `ownership unresolved` blocker has a matching sentence in findings or readiness, and nothing is called non-blocking in prose while blocking in the inventory.
- Every question and finding references the precise source ACs it affects, by `sourceId`.
- Every ownership claim cites its evidence (workspace inventory, agreed assignment, product statement) or is explicitly open.
- Every interpretation of the source that the pinned evidence does not establish (verbatim AC text, explicitly approved responses, cited code) is marked as an assumption with the evidence behind it.
- The provenance table covers every path under the run, and no row uses "copied", "adopted" or "approved" interchangeably.

Run an independent read-only review via [cross-review](../cross-review/SKILL.md), `requirements` mode, with this run's refinement artifacts and the complete scoped baseline, responses, engineering constraints and code evidence as ground truth; keep its output under `runs/<run-id>/refinement/reviews/` and maintain its single authoritative round record in the run README as specified in the run layout. Readiness and project summaries link to that record instead of copying mutable review status. A review result applies to the input state it reviewed; a new run or a changed inventory needs a new review. For repeat rounds, also supply the relevant prior findings/questions and input-change evidence; ask the reviewer to check their complete reconciliation and package-wide consistency. Record defects through the existing findings helper. Product questions remain in their exchange artifacts and cannot be resolved or auto-deferred by that review.

Produce `runs/<run-id>/refinement/readiness.md` with pinned inputs, integrity result, repo baseline status, coverage, blocking questions, dependencies and next owning skill. Check every source requirement has implementation and verification ownership across the affected repositories, or is listed as explicitly open. Do not require each repo to implement the entire baseline. Prepare self-contained pinned bundles in `runs/<run-id>/refinement/repo-handoffs/<repo-key>/` only for repositories whose ownership and scope are settled, or give a reproducible pinned acquisition procedure; never depend on another developer's absolute paths or sibling layout. Do not build the full artifact tree ahead of settled ownership.

Report status with the distinct words from the run layout: `local draft`, `branch published`, `PR open`, `reviewed`, `approved by <owner>`, `merged`, `team accepted`. A local seal, a published branch or an unauthenticated 404 from a hosting API proves neither team acceptance nor the absence of a PR; record the probe that was made and the next step that would produce the missing evidence. Reuse an existing intake instead of starting a duplicate. Shared decisions and integration evidence stay in the agreed team coordination location through its normal review process.

Each implementation repo uses its own project ID, checkout/worktree, state, tests and PR. Shared architecture records repository boundaries and versioned interfaces; local plans declare external dependencies. Feature-wide completion requires aggregate coverage, compatible revisions, required integration evidence and release ordering. One green repo or open PR is not feature acceptance.

## Session handoff

Finish refinement checks and its independent review here. Close the run with at most five prioritized next decisions (each with owner, blocked step and recommendation) and one concrete follow-up assignment, both in the run README and the project README; a long list of abstract blockers is not a closing report. Then stop at a copyable prompt for a new user-started session. Do not auto-invoke architecture, intake, bootstrap or another producing skill; `/compact` is not a new session. Name the next skill, actual bound checkout/worktree, local project identity, pinned input/response revision, inventory and readiness paths, scope and blockers. Use machine-local paths only in the personal prompt, not shared artifacts. If the checkout is missing, give its onboarding action instead of inventing a `cd` path. Do not hand blocked scope to architecture or implementation; prepare the product return package or baseline-resume prompt instead.
