# Delivery Workspace

Establish where the team coordinates a received handoff and where this developer works. Read [references/workspace-contract.md](references/workspace-contract.md) for the portable inventory, discovery/creation procedure and baseline evidence. This skill owns workspace setup; `handoff-refinement` reuses its inventory for each incoming version.

1. Discover in order: explicit team remote/identity, valid inventory and checkout, bounded inspection of current and user-supplied neighboring repositories. Inspect Git roots, remotes and the coordination marker; directory names are not ownership evidence. Ask which owner to use when ambiguous. If none is identified, request its address or search only the selected organization with authenticated provider tools. An inaccessible remote is an access blocker; an unmarked repository is legacy/unregistered. Neither permits replacement or overwriting.
2. Reuse a matching checkout without resetting or switching branches. Clone a known remote into an unoccupied path when onboarding calls for it. For a missing remote, make provider, owner, name, visibility and minimal README/inventory concrete, check existing authorization, and create only within it. Follow the bounded procedure in the reference; never infer public visibility. Use private secret entry/authentication tools if needed, never chat secrets. Resolve access or offer explicitly selected temporary local-only staging; do not claim team readiness there.
3. Record portable identities in `delivery-workspace.json` at the agreed tracked coordination location. Keep local checkout bindings outside versioned content. A dedicated specifications repository is optional: a tracked location in one implementation repository works. Do not create empty placeholder trees, initialize a code checkout's parent as Git, track nested repositories, or clone unrelated repositories.
4. Read the incoming manifest/README for the prototype inclusion decision and actual format, and carry that context into the refinement prompt. A packaged prototype or its source repository is a reference, not automatically an implementation repository: do not register it for intake/bootstrap unless the agreed repository ownership explicitly assigns it implementation work. Missing promised prototype files go to `handoff-refinement` as a package discrepancy; they do not block unrelated workspace setup. Inspect each affected implementation repository's baseline and visible active intake branches/PRs. Return a checklist containing repo key, actual checkout or actionable missing-path instruction, status, evidence, owning next skill and copyable session prompt. Reuse accepted baselines; resume incomplete intake; coordinate active intake with its owner. Do not rerun sealed intake for a new package or infer completeness from `docs/PRODUCT.md`. Propose drift audits only from evidence. Coordination-only repositories need no application baseline. Planned repositories go to the existing greenfield/bootstrap path using approved scope.
5. Keep shared changes on the team's normal review path. Record local drafts, proposed PRs and accepted revisions distinctly. Pin inputs to accepted commits/content hashes. Reconcile upstream changes and conflicting answers before readiness; no force-push, last-write-win, distributed lock or new approval system.

Recommend sibling checkouts under a plain `work/` directory for convenience (`delivery-specs/`, `frontend/`, `backend/`), without requiring that layout. Non-sibling paths, worktrees and spaces work. In apps that bind sessions to repositories, bind the next session to its actual repo/worktree; a prompt saying `cd` does not bind it.

Finish setup and its checks here. Do not auto-run intake, bootstrap or refinement. Provide separate copyable start prompts naming the owning skill, actual checkout, inventory and pinned handoff context. Intake must keep its interview and seal process. Preliminary read-only refinement and product-question preparation may start before every baseline is ready; architecture/planning/execution still check the relevant repository prerequisites. The ordinary linear chain has no new inventory or team-approval requirement.
