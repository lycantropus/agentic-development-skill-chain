# Refinement run layout

A reader opening the coordination project must see at once which refinement run this is, which handoff it examines, which files arrived unchanged, which results are new, and whether each result is a proposal, a checked result or an explicit acceptance. This layout exists for that; it adds no state system. Execution state stays in each implementation repository.

## What a run is

A run is one coherent refinement of one frozen input state. Review rounds, developer discussions, a day change or a resumed session belong to the same run as long as the handoff version and the examined repository revisions are unchanged. Create a new run when a new handoff version arrives, when the examined repository baselines change materially, or when the team deliberately starts a fresh assessment. Earlier runs stay as they were; never rewrite or delete them.

Run IDs are `YYYY-MM-DD-NN`: the local date the run started plus a two-digit counter that separates runs started the same day (`2026-10-25-01`, `2026-10-25-02`). Resuming a run on a later day keeps its ID; the run README records the continuation. Before creating a run, list `runs/` and decide: resume if the current run's handoff version and baselines still hold, otherwise create the next ID and name the predecessor.

## Layout

```
<coordination-project>/specs/PROJ-<id>-<theme>/
├── README.md                    current run, status, key results (new per project)
├── external-handoff.json        resolver marker; fixed path, see below
├── refinement/integration.json  shared integration report; fixed path, written after integrated verification
└── runs/
    └── YYYY-MM-DD-NN/
        ├── README.md            run identity, input state, provenance table, rounds, decisions
        ├── handoff/
        │   └── <source-version>/   received files, byte-identical, links untouched
        └── refinement/
            ├── findings.md             new analysis: evidence, classification, dispositions of earlier items
            ├── engineering-requirements.md  ENG constraints and optional engineering stories with authority
            ├── readiness.md            readiness report (feedback-and-readiness.md)
            ├── product-feedback/<round>/   portable return rounds to Product
            ├── reviews/                cross-review results persisted for this run
            └── repo-handoffs/<repo-key>/   derived pinned bundles per implementation repo
```

Create directories only when writing content into them. `handoff/<source-version>/` is the only place for received bytes; copy, never edit, and keep every version. The marker's `sources[].path` entries point into it, for example `runs/2026-10-25-01/handoff/v3/02-prds/PRD-1.md`.

Fixed paths outside `runs/`:

- `external-handoff.json` stays at the project root because every validator, gate and context compiler reads it there. It belongs to exactly one run: its `sources[].path` entries name that run's `handoff/` directory, and the project README names the same run. When a new run supersedes the inventory, the marker moves with it; the old run's README keeps the old inventory's fingerprint for reference.
- `refinement/integration.json` at the project root is the shared integration report read by `chain render pr`. It is pinned to the inventory fingerprint, not to a run, and is written only after integrated verification.
- Review defects go through the existing findings helper and stage ledger; `runs/<run>/refinement/reviews/` holds the human-readable review output copies, not a second ledger.

## Provenance table

Every run README carries this table. One row per path or file group; no row may leave origin or binding ambiguous.

| Path or file group | Origin | Purpose | Binding |
|---|---|---|---|
| `handoff/v3/**` | received unchanged (SHA-256 in `external-handoff.json`) | product baseline as delivered | product-owned, immutable |
| `refinement/findings.md` § Evidence | copied or extracted from `<repo-key>@<commit>` | code evidence cited by path and line | observation; neither a proposal nor an approval |
| `refinement/findings.md`, `engineering-requirements.md` | newly written in this run | engineering analysis and constraints | engineering proposal unless marked as a discussed engineering decision with rationale |
| `refinement/product-feedback/<round>/` | newly written in this run | questions to Product with evidence | questions, not approved product answers |
| `refinement/reviews/` | generated by cross-review | independent review of this run's input state | observation until a result exists; then checked for its recorded input fingerprint, not a product or team approval |
| `refinement/repo-handoffs/<repo-key>/` | derived from the inventory and received files | self-contained input bundle per repository | derived; actionable only when `chain check inputs` passes without `--allow-blocked` |

Use these origin words and no others: `received unchanged`, `copied or extracted from <source>`, `newly written`, `generated by <tool>`, `derived from <inputs>`. Use these binding words: `immutable`, `observation`, `proposal`, `discussed engineering decision`, `question`, `checked`, `approved by <owner> on <date>`, `derived`. A file that was copied is not thereby adopted; a file that was adopted in substance is not thereby approved. Say which one applies.

## Project README

`specs/PROJ-<id>-<theme>/README.md` is short and points to the current run:

```
# PROJ-<id> <theme> — external handoff refinement

Current run: runs/2026-10-25-01 (status: in progress | awaiting product answers | ready for architecture | superseded)
Handoff: <baseline id>@<version>, received <date>, integrity: verified by chain check inputs on <date>
Key results: <three to five lines: decisions needed now, scope state, readiness per repository>
Earlier runs: runs/2026-10-18-01 (superseded by v3 handoff)
```

## Run README

`runs/<run-id>/README.md` records, briefly:

- Run ID, start date, continuation dates, and the predecessor run if any.
- Handoff version and integrity proof (where the hashes live, when they were last verified).
- Examined repository revisions: repo key, commit, baseline status from workspace onboarding.
- The provenance table above.
- Current results: scope and ownership state, open decisions (at most five, prioritized), readiness per repository.
- Review rounds: round number, reviewer provider, date, result reference under `refinement/reviews/`. A clean review is a checked state of this run's inputs, not a product or team approval.
- Changes against the previous run: new handoff version, changed baselines, dispositions of earlier questions and findings by ID.
- Status vocabulary for every artifact and every repository: `local draft`, `branch published`, `PR open`, `reviewed`, `approved by <owner>`, `merged`, `team accepted`. Each status names its evidence; missing evidence names the next step that would produce it.

## One review status per round

The run README owns the review-round record: round, provider, input fingerprint
(inventory plus examined evidence revisions), status, result path and reconciliation
references. Readiness and project summaries link to this record; do not repeat
“pending”, “completed” or “clean” in independently maintained prose. Provenance
stays `observation` until a review output actually exists.

Use `pending` before output exists, `reviewed-with-findings` after receiving defects,
and `reconciled` when their dispositions and changed inputs have been recorded.
`clean` requires a review result for the current fingerprint with no unresolved
blocking review findings. A changed inventory/evidence state gets a new `pending`
round; preserve the old record and never extend its clean verdict to new inputs.
Product answers and team acceptance remain separate authority.

Behavioral check when changing this workflow: simulate pending → reviewed-with-findings
→ reconciled, then change one inventory entry. The old review must retain its old
fingerprint; only a new pending round and a new clean result may establish clean
status for the changed input. Open readiness and project summaries at every step:
they must resolve to the same authoritative record, with no independent status text.
